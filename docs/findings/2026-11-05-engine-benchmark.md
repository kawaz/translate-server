# 翻訳エンジンの比較 (2026-11-05)

claude-ccmsg の thinking 翻訳 (英→日、技術的推論文) を題材に、ローカルの翻訳エンジンと LLM CLI を同じ入力で比べた。計測は workboard-personal の incubator (`ideas/translate-bench`) で行い、ここには結論に使った数値だけを写す。

## 条件

- Apple M1 Max 64 GB、macOS 26.5
- 入力: 16 段落 (コード識別子・パス・コマンド入り、日英混在、改行入り)
- 品質の観点は既知の崩れ 3 箇所: 06 (英文の間の日本語段落と空行を保つ)、07 (改行を増やさない)、10 (行内の日本語文とインラインコード `not measured` を保つ)

## 日英混在文の丸投げ (8 ケース)

日本語のみ / 日本語主体 + 英単語 / 半々 / 英語主体 + 日本語 1 文 / 英語の技術用語入り日本語 / 複数行混在 / 敬体混在 / コードブロック入り。

| 観点 | PLaMo 3 0.8B (`form=plain`) | sol low |
|---|---|---|
| 日本語のみ | 無傷 | 無傷 |
| 半々、英語主体 + 日本語 1 文 | 英文は訳し、日本語文も訳文調に言い換える (「扱い」→「処理だ」、stdin → 標準入力) | 英文だけ訳し、日本語文は一字も変えない |
| 日本語文中の英単語 | `clean` / `push` / classifier / permit / allow を保持 | classifier → 分類器、allow → 許可と訳す |
| 複数行、コードブロック | 行構造とコードブロックを保持 | 同じ |
| エラー・再翻訳での破壊 | なし | なし |

どちらも丸投げで壊れないので、日本語比率で翻訳の要否を判定する前処理は不要にできる。

## 1 リクエストに丸ごと渡す

7 段落・693 トークンのレビュー文書を分割せず 1 リクエストで送ると、2.8 秒で 7 段落が揃って返り (脱落・結合なし、`finish_reason: stop`)、文脈が効いて係り受けの判断が良くなる箇所と悪くなる箇所が 1 つずつあった。上限は入出力合計 32,768 トークン。全文が返るまで最初の 1 文字も出ないので、逐次表示が要る用途は段落分割、要らない用途は丸ごとでよい。

## 文体の制御

`form` (`plain` / `polite`) で常体 / 敬体が揃う。`glossary` で語の訳し方を固定できる。`context` は内容理解のヒントで、文体の指示としては効かない (「日本語文を変えるな」は部分的にしか効かなかった)。英数字と和文の間の空白は入らない。
