# 文体バリエーション (お嬢様言葉、ずんだもん、侍 ほか 17 種) をプロンプト層で出せるか

- Date: 2026-11-07

PLaMo 3 Translate 0.8B に、リクエストの中身だけ (再起動・学習なし) でキャラクターの口調を付けられるかを実機で確かめた。17 文体 × 4 本の英文 × 3 通りの渡し方を全部通し、出力をそのまま表に貼る。

## 判明した事実

- **文体の指示を受け取る口は `form` (常体 / 敬体) と `target_lang: "ja(easy)"` (やさしい日本語) の 2 つだけで、どちらも効く。** それ以外の口調は、`context` に説明を書いても、例文 (history) を 7 対積んでも、`glossary` で一人称を固定しても出ない。17 文体の目印語 (「のだ」「ござる」「ですわ」等) が出た文は、どの渡し方でも 12 文中 0〜1 文
- `system` メッセージは chat template が捨てる (`chat_template.jinja` の 27〜41 行目、先頭の system turn を数えて `messages` から外す)。公式モデルカードも「system message ではなく template 引数で指定する」としており、文体の口は `form` だけと書いている
- 例文 (history) は、口調の **性別・粗さ・硬さ** を少しだけ寄せる。「すごいわね」「〜と思っていたわ」(お嬢様)、「行こうぜ」「食いに行こう」(熱血・江戸っ子・ネットスラング)、「行こうにゃ」(猫、4 文中最後の 1 文だけ)、「実行せよ」(侍・老人・中二病)、「書店」「長年」「待ちわびていた」(執事・ロボット・中二病) が出た。キャラクター固有の語尾や語彙は出ない
- 例文を積むと訳の意味がずれることがある。長文の「a letter she had never dared to open」が、既定の「開く勇気のなかった手紙」から、幼児で「めったに開けない手紙」、敬語ビジネスで「めったに開く勇気のない手紙」になった (17 文体中 2 件)
- 文末を grammar (GBNF) で「のだ」「ですわ」に強制すると、最初の 1〜2 文は付くが、その後は原文に無い文 (「」私はそう言ったのだ。」の繰り返し等) を `max_tokens` まで出し続けて止まらない
- 常体の訳文に正規表現で文末だけを付け足す後処理は、「にゃ」はほぼ自然、「のだ」は半分ほど自然、「ござる」は不自然 (「ありがとうのでござる」「行こうのでござる」)。一人称や語彙 (拙者、かたじけない) は置き換えられない
- `temperature: 0` でも同じ入力の訳が 1 語揺れた (204 リクエストを 2 回通して 1 件、「開く勇気のなかった」→「開く勇気のない」)。原因は未確認 (他セッションのリクエストとの同時 decode、prompt cache の再利用が候補)

## 実用的な示唆

### 渡し方ごとの分類

| 分類 | 文体 | 根拠 |
|---|---|---|
| プロンプト層で効く | 常体、敬体 (`form`)、やさしい日本語 (`target_lang: "ja(easy)"`) | 全 4 本で指定どおり。翻訳精度の劣化なし |
| 口調が少し寄るだけ | お嬢様言葉 (女性語「わ」)、熱血・江戸っ子・ネットスラング (男性語「ぜ」、くだけた語彙)、執事・ロボット・中二病・敬語ビジネス (硬い語彙。ロボットのカタカナ表記、ビジネスの「恐れ入りますが」等の定型句は出ない) | 例文で寄るのは日本語として普通の範囲の言い回しまで |
| 効かない (指示を無視) | ずんだもん、侍、ツンデレ、関西弁、幼児、ギャル、ハードボイルド、関白風の老人 | 目印語 0/12。既定の訳とほぼ同じ |
| 文体が混ざる | 猫キャラ | 4 文中最後の 1 文だけ「にゃ」 |
| 崩れる | grammar で文末を強制した全文体 | 原文に無い文を出し続ける |

指示を無視するので、プロンプト層の工夫では翻訳精度はほとんど落ちない (例外は上の「めったに」の 2 件)。代わりに文体も付かない。原因はモデルの側にある: 入力形式 (PFML) に文体の口が `form` しか無く、翻訳専用に学習された 0.8B なので自由文の指示に従う能力が無い。「(1) プロンプトで当たりを付けてから (2) LoRA に落とす」の順のうち (1) は、このモデルでは `form` と `ja(easy)` の 2 択で終わる。

### キャラクター文体を出す経路の候補

| 経路 | 出せるもの | 費用 | 状態 |
|---|---|---|---|
| A. 後処理 (常体の訳文の文末を書き換える) | 語尾だけで成り立つ文体 (猫、ずんだもん)。語彙が要る文体 (侍、関西弁、お嬢様) は無理 | ゼロ。front の JS で書ける | 本 findings でデモ済み |
| B. LoRA (PLaMo 3 Translate に文体ごとのアダプタ) | 語尾も語彙も。訳の正確さを保ったまま付けられる見込み | データ整備と学習。下記の見積り | 未着手 (kawaz 裁定待ち) |
| C. 2 段 (翻訳 → 汎用 LLM で口調を書き換える) | 何でも (指示文で切り替え) | 汎用モデルを別に動かす (4B 級で 2〜3 GB、1 段落 1 秒前後の見込み) | 未検証。手元の Qwen3 / gemma 3 は refs だけで重みが無い |
| D. 言語タグの埋め込みを書き換える | 報告者の出力例はお嬢様の語尾 (〜ますわ、〜くださいまし、〜ですの)。報告者は部分的な学習より精度が少し落ちると書いている | 推論時はゼロ。値を決めるのに HF の元モデルと「どの場面でどの語尾を選ばせたいか」の一覧が要る | 未検証 (下記) |

#### D. 言語タグの埋め込みの書き換え

一次情報は X の投稿スレッド (@rizumita、2026-11-05〜06。2026-11-07 に第三者の公開 API `api.fxtwitter.com` 経由で本文を取得)。要点:

- 同じモデル (HF 版の safetensors) で、Opus に重みを書き換えさせてお嬢様言葉にした。変わったのは `model.safetensors` だけで、全 890,344,960 値のうち 1,534 値、すべて `ja` (トークン id 1385) の埋め込みの 1 行。行のノルムは 85.31 → 97.09
- 出力例: 「光は音よりも速く進みますわ。」「エラーが解消されない場合は、システム管理者に問い合わせてくださいまし。」「京都行きの電車はどれですの？」
- 値の決め方 (後続の投稿で訂正): 「どの場面で、どの語尾をもう少し選ばせたいか」を全部書き出し、それを満たす直し方を最小二乗法 1 回で解いた。部分的な学習と比べると精度は少し落ちた
- 投稿時点では、本人は外出中で結果を直接確認できていないと書いている。他の文での安定性、訳の正確さへの影響は書かれていない

この環境で確認できた前提:

- この環境の tokenizer でも、出力側の `<|plamo:val|>ja<|plamo:msg|>` の `ja` は 1385。埋め込みは 1,536 次元 (`n_embd`) なので、報告の 1,534 値はほぼ行全体
- GGUF の `token_embd.weight` は Q4_K で、`output.weight` (Q6_K) とは別のテンソル (重み共有なし)。入力側の行を変えても、出力の語彙確率には直接響かない
- 書き換えた行は Q4_K に再量子化されるので、差分が量子化誤差に埋もれないかを確かめる必要がある。HF の元モデルで行を変えてから GGUF に変換・量子化するのが素直
- 必要なのは、元モデル (safetensors) と、場面と選ばせたい語尾の一覧 (`styles.json` の例文 7 対から作れる)。勾配で回す学習は要らない

LoRA に対する利点の候補:

- 解くのが 1,536 次元の 1 行だけで、最小二乗法 1 回で済む
- 推論時の追加費用が無い
- `--lora` を per-request で切り替えた時に起きうる並列の直列化を避けられる
- 使っていない言語コードの行 (1 トークンで表される訳先コード。この tokenizer で `ko`=1464、`ru`=2086、`vi`=2190 などを確認) に文体の埋め込みを入れれば、1 つの GGUF のまま `target_lang` で文体を選べる見込みがある (その言語への翻訳は使えなくなる)

どれも未検証。語尾は寄せられても、語彙 (わたくし、拙者) や関西弁の活用まで 1 行で寄るかは分からない。

### LoRA に落とす価値があるもの

後処理 (A) で足りず、使い道があるものを優先する。

1. ずんだもん: 語尾は A でも半分出るが、「ありがとうなのだ」のような活用込みの自然さと一人称「ボク」は A では出ない。人気が高く、最初の 1 本に向く
2. お嬢様言葉: 例文で女性語までは寄るので、LoRA で語彙 (わたくし、ごきげんよう、存じますわ) を足す差分が小さい
3. 侍: 語尾 (ござる) と語彙 (拙者、かたじけない、申す) の両方が要り、A では最も不自然
4. 関西弁: 語尾でなく語彙と活用 (〜へん、ほんま、〜しとる) の置換で、A では不可能
5. 執事: 敬体 + 謙譲語・定型句の上乗せで、訳の正確さを崩しにくい

ツンデレ・中二病・ギャル・ネットスラングは、原文に無い言葉 (「べ、別に〜じゃないんだからね」「ククク」) を足すのが文体の本体で、翻訳として正確であることと衝突する。LoRA に落とすなら翻訳でなく C の書き換えの方が筋が良い。

### LoRA の設計案と工数見積り (未着手)

- 学習データ: 英文 → 常体訳 (PLaMo 自身の出力) → Claude などの強い LLM で文体に書き換え → (英文, 文体付き訳) の対を 1 文体 1,000〜2,000 対。英文は利用先に近いもの (ccmsg の thinking 段落、会話文、技術文) を混ぜる。書き換え時に「意味を足さない・削らない」を指示し、抜き取りで検品する
- 学習: HF の `pfnet/plamo-3-translate-0.8b` に PEFT で LoRA (attention + MLP、r=16 前後)。プロンプトは chat template と同じ PFML (`form=plain`) で組み、出力側だけに loss をかける。M1 Max の MPS で回る規模 (0.8B)
- 変換と配信: llama.cpp の `convert_lora_to_gguf.py --base <HF の元モデル>` で GGUF アダプタにし、`bin/translate-server` に `--lora` を足して起動。既定で全リクエストに効かないよう `--lora-init-without-apply` を付け、リクエストごとに `"lora": [{"id": N, "scale": 1.0}]` で選ぶ
- 先に潰すリスク (外れると設計全体が変わる順):
  1. `convert_lora_to_gguf.py` が PLaMo 3 のアーキテクチャに対応しているか (ダミーの LoRA を 1 step 学習して変換が通るか)
  2. PEFT が PLaMo 3 の独自実装 (`trust_remote_code`、numba 依存) に掛かるか
  3. `--parallel 4` で、アダプタの違うリクエストが同時に来た時に直列化されて遅くならないか
  4. Q4_K_M の本体に f16 のアダプタを載せて文体が保たれるか
- 見積り (どれも未検証の見込み):
  - リスク 1〜3 の確認: 0.5 日
  - データ生成の仕組み + 1 文体分のデータ: 0.5 日
  - 学習・変換・評価 (1 文体): 0.5 日
  - 2 文体目以降: 各 2〜3 時間 (生成と学習は自動、評価に人の目が要る)
  - パイロット 1 文体で約 1.5 日、上の 5 文体で約 2.5〜3 日
- 文体ごとに別アダプタにするか、1 本のアダプタに全文体を学習させて `context` の札 (例: `style:zundamon`) で切り替えるかは、パイロットの結果を見て決める。前者は文体の追加が独立で混ざらない代わりにアダプタが増える、後者は 1 本で済む代わりに文体同士が混ざる恐れと、`context` を本来の用途 (内容のヒント) に使いにくくなる

### front (ccmsg) から使う形の提案

文体を選ぶ UI は、文体 ID → リクエストの差分 (+ 後処理) の対応表を front 側で持つのがよい。

```js
// 例: front の対応表。chat_template_kwargs と lora はリクエストにそのまま混ぜる
const styles = {
  plain:    { label: "常体", kwargs: { form: "plain" } },
  polite:   { label: "敬体", kwargs: { form: "polite" } },
  easy:     { label: "やさしい日本語", kwargs: { target_lang: "ja(easy)" } },
  neko:     { label: "猫", kwargs: { form: "plain" }, post: nekoEndings },      // 後処理 (A)
  zundamon: { label: "ずんだもん", kwargs: { form: "plain" }, lora: "zundamon" }, // LoRA (B) ができたら
};
```

- 今出せるのは `form` と `ja(easy)` と後処理だけなので、対応表を translate-server 側に置く理由がまだ無い (DR-0002 の「このリポは API を定義しない」のまま)
- LoRA を入れた後も、translate-server に新しい API は要らない。llama-server の `GET /lora-adapters` は読み込んだアダプタの ID とパスを返す (この環境はアダプタ未ロードで `[]` を確認) ので、front はファイル名から ID を引ける (起動順で ID が変わっても壊れない)。文体名とファイル名の対応を README に表で書けば足りる
- キャッシュの鍵には文体 ID を含める (同じ原文でも文体ごとに訳が違う)
