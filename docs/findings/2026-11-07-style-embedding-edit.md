# 言語タグ `ja` の入力埋め込み 1 行だけを書き換えて訳文に口調を付けられるか

- Date: 2026-11-07

[文体バリエーションの findings](2026-11-07-style-variations.md) の経路 D (言語タグの埋め込みの書き換え) を実機で確かめた。PLaMo 3 Translate 0.8B の `ja` (token id 1385) の入力埋め込みの行に差分 Δ を足し、お嬢様言葉・ずんだもん・侍・関西弁が出るかを見た。Δ は (a) 最小二乗法 1 回と (b) その 1 行だけの学習の 2 通りで求め、公式 GGUF (Q4_K_M) のコピーに書き込んで llama-server で評価した。

## 判明した事実

- **(a) 最小二乗法 1 回では、どの解でも口調が出なかった (llama-server、HF 版とも目印語 0/12)。** 場面の取り方を 4 通り、λ を 0.01〜10 (|Δ| = 4〜408) まで変えても同じ。X 投稿の 3 文 (Light travels faster than sound. ほか) も |Δ| = 408 まで既定の訳のままで、投稿の「〜ますわ」「〜くださいまし」「〜ですの？」は再現しなかった
- (a) が効かない理由は 1 次近似の精度ではなく、1 行の差分で全場面を同時に満たす解が線形の範囲に無いこと。1 次近似の予測と Δ を入れて流し直した実際の margin の相関は |Δ|≈10 で 0.99、|Δ|≈100 で 0.89 と十分合っている。それでも線形の解の時点で「選ばせたい場面」が勝つのは 3〜30% にとどまり、そこまで上げると |Δ| が 150〜250 になって、訳先の言語そのものが変わる (ずんだもん用の解で、日本語の代わりに韓国語・ベンガル語が出た)
- **(b) 1 行だけの学習では、語尾の一部と語彙の一部が出る。ずんだもんが最も効き、お嬢様・侍は少し、関西弁はほぼ出ない。** llama-server (Q4_K_M) で 1.0 倍のとき、目印語はずんだもん 5/12、お嬢様 1/11、侍 1/12、関西弁 0/12。HF 版 (fp32) ではずんだもん 8/12 で、量子化した本体では効きが落ちる
- (b) は複数文の訳で口調が続かないのが最初の壁だった。学習データ 52 対 (1〜2 文) だけで学習すると、学習データから外した 10 文では 9/10 に「のだ」が付くのに、評価用の 4 本 (2〜4 文) では 1/12。学習データの対を 2〜4 個つないだ 30 対を足すと 8/12 (HF 版) になった
- 口調が付いても訳の意味は崩れやすい。お嬢様で「never dared to open」→「めったに開く勇気のない」(誤訳)、関西弁で「人ほぼいんかった」(文法崩れ)・「she」→「あいつ」(性別の脱落)、ずんだもん 1.5 倍で「人がいなのだ」(崩れ)。form=plain を指定しても敬体になる (お嬢様)、句点が全角ピリオド「．」になる (お嬢様) 例も出た
- **Δ の大きさは 1.0 倍付近でしか効かない。** 0.5 倍は 4 文体とも既定の訳とほぼ同じ (0/12)。1.5 倍は ずんだもん・侍で目印が少し増えるが、ずんだもんの会話文が韓国語になり、お嬢様・関西弁は逆に口調が消えた (単調に強くならない)
- **派生案 (使っていない言語コードの行に文体を入れる) は、その形のままきれいに動いた。** `ja` 行は元のまま、`ko` 行 = `ja` 行 + Δ(ずんだもん)、`ru` 行 = `ja` 行 + Δ(お嬢様) にした 1 つの GGUF で、`target_lang: "ja"` の訳は Δ=0 の GGUF と 8 本すべて同一、`ko` + `form=plain` の訳は `ja` 行を書き換えた GGUF の訳と 4 本すべて同一、`ru` + `form=polite` も同様に一致した。リクエストごとに文体を選べる
- ただし chat template は `form` に `target_lang="ja"` を要求するので、`ko` / `ru` で `form` を付けるには PFML を直に組んで `/completion` に送る必要がある。`form` 無しで `ko` を指定すると訳が変わる (「助けてくれてありがとうなのだ」が付く代わりに、長文が「人がいなのでした」と崩れて敬体になる)
- GGUF の加工 (token_embd を F32 に dequantize して行を書き換え、他のテンソルは元の量子化のまま書き戻す) は gguf-py でそのまま書けた。HF の `ja` 行 (先頭 -1.1797, 1.2813, -1.2813, 2.4375、ノルム 85.31) と GGUF を dequantize した行 (-1.2175, 1.2156, -1.2175, 2.4322、ノルム 85.32) は同じ尺度。Δ=0 で加工した GGUF は公式 GGUF と 16 本 (ja plain / ja polite / ko / ru × 4 本) すべて同じ訳を出した
- Δ を求める所要時間: (a) はヤコビアン (場面ごとの勾配) に 30〜230 秒、解くのは 1 秒前後。(b) は 8 epoch で 70〜145 秒 (お嬢様は 2 form 分で倍)。M1 Max の MPS、HF 版 fp32

## 実用的な示唆

### 経路 D の位置づけ

| 観点 | 評価 |
|---|---|
| 口調を付ける力 | 語尾だけで成り立つ文体 (ずんだもん) で、4 本中 2〜3 本の一部の文に付く程度。全文に安定して付くところまでは届かない |
| 訳の正確さ | 1.0 倍でも誤訳・文法崩れが 4 文体で計 5 件。既定の訳 (プロンプト層) より明らかに悪い |
| 推論時の費用 | ゼロ (GGUF の 1 行を差し替えただけ。token_embd を F32 にしたので GGUF は 570 MB → 1.14 GB) |
| 1 つの GGUF で文体を選ぶ | 可能。使っていない言語コードの行に入れれば `ja` の訳は 1 文字も変わらない |

「最小二乗法 1 回で 1 行を直せば口調が付く」という一次情報の主張は、この環境では再現しなかった。1 行の学習 (b) でも、語尾が一部に付くまでで、LoRA の代わりになる水準ではない。経路 B (LoRA) の見積りは変えなくてよい。

一方で派生案の「言語コードの行を文体の口として使う」仕組みは、LoRA と組み合わせられる可能性がある (未検証): LoRA を全リクエストに掛けたまま、文体ごとに学習した `ko` / `ru` 行で切り替えれば、`--lora` の per-request 切り替えを使わずに済む。

### 次に試すなら (未着手)

- (a) を反復する (Gauss-Newton で 3〜5 回線形化し直す)。1 回で効かない原因が線形化点の遠さだけなのかを切り分けられる
- (b) で学習する行を `ja` 1 行から PFML の他のトークン (`<|plamo:msg|>`、`form` の値) に広げる。それでも効きが足りなければ、1 行の上限と見なして LoRA に進む
- 学習データを増やす (1 文体 52 対 + 連結 30 対では、関西弁のように語彙と活用の置き換えが要る文体はほとんど学べていない)

## 検証の詳細

### 条件

- Apple M1 Max 64 GB、llama.cpp b12110 (Homebrew)
- Δ の計算: HF 版 `pfnet/plamo-3-translate-0.8b` (model.safetensors、bf16 を fp32 で読む)、PyTorch 2.15 (MPS)、transformers 5.22。この版の `scale_embedding` は false で、入力埋め込みは素の `nn.Embedding` (√1536 倍しない)
- 評価: 公式 `plamo-3-translate-0.8b-Q4_K_M.gguf` のコピーを `make_gguf.py` で加工し、`bin/translate-server` と同じオプション (`--chat-template-file chat_template.jinja --no-prefill-assistant --alias plamo-3-translate`) に `-c 4096 --parallel 1` を付けて 127.0.0.1:18087 で起動。`/v1/chat/completions`、`temperature: 0`、`finish_reason` は全件 `stop` (`/completion` 直組みは `eos`)
- 目印語の数え方は先行 findings と同じ (訳文を「。！？」で文に分け、`styles.json` の `markers` を含む文を数える)
- 評価文は `styles.json` の tests 4 本 (短文・会話文・技術文・長文)。学習データには入れていない

### 学習データ

`data/` に置いた。英文 45 文 (`sources.json`、会話 18・技術 14・物語 13) と、文体ごとの和訳 (`ojousama.json` / `zundamon.json` / `samurai.json` / `kansai.json`) を自分で書いた。`styles.json` の例文 7 対と合わせて 1 文体 52 対。評価用の 4 本と同じ話題 (礼と別れ、レポート、stdin とセットアップ、雨と本屋と手紙) は避けた。さらに `common.concat_pairs` で 52 対から 2〜4 対をつないだ 30 対を作って足した (複数文でも口調が続くように)。お嬢様は評価で polite も見るので、同じ対を form=plain と form=polite の両方で学習した。

### (a) 最小二乗法 1 回

`solve.py jac` で場面ごとの margin (正解トークンのロジット − それ以外で最も高いトークンのロジット) と、その Δ についての勾配を取り、`solve.py lsq` で「上げたい場面は margin を 2 まで上げ、他の場面は今の margin を保つ (重み 0.3)」連立式をリッジ最小二乗で 1 回だけ解いた。場面の取り方を順に変えた記録 (HF 版、tests 4 本の目印語):

| 場面の取り方 | 場面数 (上げる) | λ と \|Δ\| | 結果 |
|---|---|---|---|
| 学習データの訳文の全トークン。既定と違うトークンを全部上げる | 574 (266) | λ=1〜10000、\|Δ\|=0.04〜97 | 0/8 (3 本で確認)。上げる場面に文体と関係ない言い回しの違いまで入る |
| 文体の語尾・語彙 (`data/lift.json` の正規表現) に当たるトークンだけ上げる + 連結 30 対 | 1538 (266) | λ=1〜10、\|Δ\|=33〜102 | 0/12 (ずんだもん)、0/12 (お嬢様) |
| 同上で、上げる量に上限 3 / 今の margin が −4 以上の場面だけ上げる | 1538 (266 / 59) | λ=0.3〜1、\|Δ\|=9〜25 | 0/12 |
| モデル自身の既定の訳の文末に語尾を差し込んだ文 (`onpolicy.py`) で、差し込みとその直後の約物を上げる | 1392〜1418 (121〜176) | λ=0.1〜10 | 0/12。λ=0.1〜0.3 (\|Δ\|=160〜250) のずんだもんで会話文・技術文が韓国語、会話文がベンガル語になった |
| 上の行で、差し込み位置の直前のトークンも上げる対象にした (下記) | 1392〜1418 (239〜246) | λ=0.3〜10、\|Δ\|=22〜160 | 0/12。llama-server でも λ=0.3 / 1 で 0/12 (ずんだもん λ=0.3 は会話文がベンガル語、技術文が韓国語) |
| 直前トークンを足す前の差し込み場面 (お嬢様) で、保つ場面の重みをほぼ 0 にした (上げる場面だけを満たす最小ノルム解) | 1392 (121) | λ=0.01〜1、\|Δ\|=79〜408 | X 投稿の 3 文が既定の訳のまま |

潰した設定の候補:

- **尺度**: HF の行と GGUF の行の値・ノルムが一致することを確認した。HF のモデルは入力埋め込みを √1536 倍しない (`scale_embedding: false`) ので、それに合わせた。Δ が効いていること自体は、大きい Δ で訳先の言語が変わることで確かめた
- **トークン位置 (実装漏れを 1 件見つけて直した)**: 「終了する。」は `['終了', 'する。']` と約物込みで 1 トークンになり、「終了するのだ。」は `['終了', 'する', 'の', 'だ。']` になる。差し込んだ範囲に重なるトークンだけを上げる対象にしていたため、「する。」でなく「する」を選ぶ場面が「今の margin を保つ」側に入り、解けない式になっていた。差し込み位置の直前で終わるトークンも上げる対象に加えた (`solve.py` の `token_flags`)。直しても結果は変わらなかった
- **BOS**: HF の tokenizer は BOS (id 1) を先頭に付け、chat template も `bos_token` から始まる。プロンプトの id 列を目視で確認した
- **form キー**: お嬢様は form=polite の既定の訳から場面を作った。form=plain / polite / なしのどれで評価しても語尾は付かなかった
- **1 次近似の精度**: `check_linear.py` で予測と実際の margin を比べた (ずんだもん、λ=1)。0.1 倍: 相関 0.99、上げる場面の勝率 予測 5% / 実際 5%。1.0 倍: 相関 0.89、予測 29% / 実際 16%。近似は外れておらず、線形の解そのものが弱い

### (b) 1 行だけの学習

`solve.py train`: Δ (1,536 値) だけを学習可能にし、訳文トークン + 終端の交差エントロピーを Adam (lr 0.05、L2 1e-4) で 8 epoch 下げた (お嬢様は 16 epoch)。|Δ| は 45〜50 に落ち着く (元の行のノルムは 85)。

| 文体 | 所要 | 最終 epoch の平均 CE | \|Δ\| |
|---|---|---|---|
| ずんだもん (連結なし) | 40 秒 | 0.72 | 45.6 |
| ずんだもん (連結 30 対) | 72 秒 | 0.72 | 45.8 |
| お嬢様 (2 form、16 epoch) | 285 秒 | 0.87 | 49.1 |
| 侍 | 78 秒 | 1.30 | 44.8 |
| 関西弁 | 72 秒 | 1.68 | 51.8 |

学習データの末尾 10 対を外した検証 (ずんだもん、連結なし): 外した 10 文の CE は Δ=0 で 3.99、学習後 0.77〜0.84 (lr と L2 を 4 通り変えてもほぼ同じ)。外した 10 文の訳は 9 文で最後の文に「のだ」が付いた。

HF 版 (fp32) でのずんだもん (連結 30 対、1.0 倍) の訳。llama-server (Q4_K_M) の結果は下の表:

| 本 | 訳文 | 目印 |
|---|---|---|
| 短文 | 助けてもらったのだ。明日会うのだ。 | 2/2 |
| 会話文 | えっ、もうレポート全部終わったの？すごいね。少なくとも一週間はかかると思ってたよ。お祝いに晩ご飯食べに行こう！ | 0/4 |
| 技術文 | ヘルパーは stdin を一行ずつ読み、config ファイルが無いと status 1 で終了するのだ。サーバーを起動する前に `just setup` を実行するのだ。 | 2/2 |
| 長文 | 朝早くから雨が降っていたのだ、通りはほとんど空いていたのだ。彼女は開く勇気のなかった手紙を持って、ゆっくりと古い本屋の方へ歩いて行ったのだ。やっと扉の前まで来ると、少しためらったのだ、そして中に入ったのだ。店主は顔を上げて、ずっと待っていたかのように微笑んだのだ。 | 4/4 |

短文は「Thank you」が「助けてもらった」になり礼が抜けた。長文は全文に付いたが「降っていたのだ、」「ためらったのだ、」と読点の前に付く不自然さがある。

### 訳の正確さの判定 (llama-server、(b) 1.0 倍と 1.5 倍、派生案)

原文と突き合わせて、意味の欠落・付加・誤訳と、日本語としての崩れを見た。下の全訳文の表のうち、既定の訳から変わったものだけを挙げる。

| 条件 | 本 | 判定 |
|---|---|---|
| お嬢様 1.0 倍 (plain / polite) | 短文 | 意味は正確。句点が全角ピリオド「．」。plain 指定でも敬体 |
| お嬢様 1.0 倍 | 会話文 | 正確。「すごいわね」「思ってたわ」(女性語まで) |
| お嬢様 1.0 倍 (plain) | 技術文 | 正確。plain 指定でも敬体 |
| お嬢様 1.0 倍 | 長文 | **誤訳**: never dared to open → 「めったに開く勇気のない」。「微笑まれました」(尊敬語) |
| ずんだもん 1.0 倍 | 短文・技術文・長文 | 正確。技術文は config / status が英語のまま。長文は 4 文中 2 文に「のだ」 |
| 侍 1.0 倍 | 短文 | 「ご助力ありがたう。明日、参るでござる。」see you → 「参る」(行く) でずれが小さくある |
| 侍 1.0 倍 | 会話文・技術文・長文 | 正確。「思っていたぞ」「実行せよ」「しばし躊躇し」(硬い男性語まで、ござるは無し) |
| 関西弁 1.0 倍 | 短文・会話文 | 正確。「ありがとな」「思ってたわ」「行こうぜ」(くだけるだけで関西弁の目印は無し) |
| 関西弁 1.0 倍 | 技術文 | 正確。「終了します」と「実行して」で敬体と常体が混ざる |
| 関西弁 1.0 倍 | 長文 | **崩れ**: 「人ほぼいんかった」。**欠落**: she → 「あいつ」(性別が落ちる) |
| ずんだもん 1.5 倍 | 会話文 | **言語崩れ**: 韓国語で出力 |
| ずんだもん 1.5 倍 | 技術文 | helper → 「助手」(誤訳寄り) |
| ずんだもん 1.5 倍 | 長文 | **崩れ**: 「人がいなのだ」 |
| 侍 1.5 倍 | 技術文 | helper → 「助手」。Run → 「走らせてくれ」 |
| 派生 `ko` (form なし) | 長文 | **崩れ**: 「人がいなのでした」、全体が敬体になる |

0.5 倍は 4 文体とも既定の訳と語の揺れ程度の差しかない。

### 派生案の照合

1 つの GGUF (`ko` 行 = `ja` 行 + Δ(ずんだもん)、`ru` 行 = `ja` 行 + Δ(お嬢様)) で:

| 比べたもの | 結果 |
|---|---|
| `ja` form=plain / polite の訳 vs Δ=0 の GGUF | 8 本すべて同一 |
| `ko` + form=plain (`/completion`) vs `ja` 行にずんだもんの Δ を足した GGUF の `ja` form=plain | 4 本すべて同一 |
| `ru` + form=polite (`/completion`) vs `ja` 行にお嬢様の Δ を足した GGUF の `ja` form=polite | 4 本すべて同一 |

### 再現

このファイルと同名のディレクトリに置いた。venv・HF のモデル・GGUF・Δ は置いていない。

- `common.py`: HF 版の読み込み、PFML の組み立て、`ja` 行を差し替えた greedy 生成。環境変数 `PLAMO_HF` に HF のモデルのディレクトリを入れる
- `solve.py`: `jac` / `lsq` が (a)、`train` が (b)
- `onpolicy.py`: (a) の場面 (既定の訳 + 語尾の差し込み) を `data/onpolicy_<style>.json` に書く
- `check_linear.py`: (a) の 1 次近似の予測と実際の比較
- `hf_eval.py`: HF 版で Δ の候補を tests 4 本で比べる
- `make_gguf.py`: 公式 GGUF をコピーし、token_embd を F32 に dequantize して行を書き換える
- `server_eval.py`: 加工 GGUF で llama-server を起動 (ログの `listening on http` の行で起動完了を待つ)、tests を訳して JSON Lines を出し、起動したプロセスだけを止める
- `eval_all.sh`: 上の評価を全条件で回して `results.jsonl` を作る。`tables.py` がこの節の下の表を出す

使ったコマンド (`$D` は Δ の置き場):

```sh
python solve.py jac <style> $D/<style>_jacop.npz --onpolicy        # onpolicy.py <style> を先に実行
python solve.py lsq $D/<style>_jacop.npz $D/<style>_lsqop.npz --lams 0.1,0.3,1,3,10
python solve.py train zundamon $D/zundamon_train_c30.npy --concat 30 --epochs 8
python solve.py train ojousama $D/ojousama_train16.npy --concat 30 --epochs 16
python solve.py train samurai  $D/samurai_train.npy  --concat 30 --epochs 8
python solve.py train kansai   $D/kansai_train.npy   --concat 30 --epochs 8
eval_all.sh <作業ディレクトリ> $D
```

### llama-server での全訳文
